engine install on disk, and compared every status claim in `context.md` and the old root documents against the
code and the evidence files in `reports/`. Evidence states follow `AGENTS.md`: `[VERIFIED]` means checked in this
session, `[REPORTED]` means taken from an earlier evidence file without re-running it, and `[UNVERIFIED]` means a
claim that has no evidence.

This audit is the input to [`04_ROADMAP.md`](04_ROADMAP.md). Every finding below names the phase that resolves it.

## 2. What is genuinely implemented and works

Each row has been run in the real engine at least once, with evidence in `reports/`.

1. **Live editor link** (`unreal/live_editor.py`). It uses the engine's own `remote_execution.py`, checks project identity, authenticates with a session token (`hmac.compare_digest` in the editor), classifies crashes, and quits gracefully. Contract test 16/16. [REPORTED 2026-10-27]
2. **Op layer.** There are 126 named ops, and every one is catalogued in `unreal/op_catalog.py`, where a unit test enforces "every mutating op names a read-back op". Native C++ libraries cover Blueprint graphs, UMG, landscape, character, animation and VFX. [VERIFIED by test]
3. **Toolchain** (`unreal/toolchain.py`). It scaffolds projects, builds with UBT and parses the diagnostics, runs automation tests, packages with BuildCookRun, and runs a packaged smoke test. [REPORTED]
4. **Prompt → packaged game** for 5 recipe families: grid (tic-tac-toe, Gomoku, N-in-a-row, Connect Four), platformer, arena, card battler and procedural world. There is also a free-form path on a host framework with a repair ladder. [REPORTED, audit 2026-10-30]
5. **Engine capability demos M8–M16** (biomes/PCG/World Partition/Data Layers, materials, Geometry Script props and kits, Niagara, audio/MetaSound, guard AI, quests with save/load, Sequencer + MRQ, CSV profiling). They pass in PIE, and the kit's packaged self-test passed 6/6. [REPORTED 2026-10-31]
6. **Asset registry** (SQLite, lifecycle, PROMOTE gated on ENGINE_VERIFY, provenance). [VERIFIED by test]
7. **Desktop IDE** (PySide6). The 7-step UX overhaul is done, and resource budgets are met (idle CPU 0.21–0.57 %, ~90 MB). [REPORTED]
8. **Models:** 4 local models via Ollama. Native tool-call self-test 4/4. The hosted tier is coded but has only been tested against a local mock. [REPORTED]

## 3. Findings (defects, gaps, weak decisions)

Severity: **S1** blocks the product goal · **S2** a correctness or trust defect · **S3** maintainability or quality.

### F-01 (S1) The capability kit is not reachable from a prompt — resolved by P5/P6
`pipeline/game_pipeline.py:101-297` is an `isinstance` if/elif chain over five hard-coded recipe parameter
classes. Everything built in M8–M16 is reachable only from `scripts/demo_*.py` or through single agent ops. That
covers materials, Geometry Script props, biomes and PCG, kit actors (`AGameForgePickup`, `AGameForgeGuard`,
`AGameForgeQuestGiver`, `UGameForgeObjectiveSubsystem`), VFX, audio and Sequencer. **A user prompt cannot produce a
game that uses any of them.** This is the central product gap.

### F-02 (S1) There is no Game Design Spec — resolved by P1
`GameSpec` (`pipeline/spec_from_prompt.py:93`) holds only `recipe_id + params + acceptance: List[str]`. The matcher is
keyword based (`RECIPES` list, line 39). The 2026 literature shows that a detailed structured specification is the
largest single lever on end-to-end game generation: Spec2Game reports a mean overall score of 50.6 with a minimal
description versus 68.6 with a detailed spec (see `03_RESEARCH_2026-10-31.md` §2). Rules and termination conditions
are what agents get wrong most often, and GameForge has no typed place to put them.

### F-03 (S2) The planner can complete without evidence — resolved by P0
- `backend/agent/plan_generator.py:265`: the default plan's only predicate is
  `TaskAcceptancePredicate(predicate_type="custom", target="inspection_complete", satisfied=True)`. It is created
  already satisfied.
- `backend/agent/task_state.py:513-515`: a `custom` predicate is evaluated by trusting its `satisfied` flag.
- `backend/agent/plan_executor.py:411-412`: `_evaluate_predicates([])` returns `(True, [])`, so a task with no
  predicates passes.
- `plan_generator.py:233` hard-codes `E:\GameForge\validation\live_ops_probe\GFProbe.uproject` as a fallback
  target. That would point the agent at a developer probe project on any other machine.
- `generate_plan_from_prompt` is keyword-templated ("unreal|actor|mesh…" → a "spawn actor" plan). It is not a planner.

These break design-contract rule 2 ("completion is evidence, not text").

### F-04 (S2) Undo coverage is far smaller than documented — resolved by P0 (audit) and P2 (project checkpoints)
The `gameforge_ops.py` docstring says "Mutations run inside ScopedEditorTransaction where the editor supports undo".
In reality `grep -c ScopedEditorTransaction` finds **8** uses, while `mutates=True` appears **73** times. Generated
projects also have no project-level checkpoint, so nothing rolls a failed stage back except deleting the project.

### F-05 (S2) Hard-coded host paths in product code — resolved by P0
There are 23 hard-coded `E:\` paths in 17 product files (full list in `handovers/P00_foundation.md` §WI-0.2). Examples:
`launcher.py:17` and `backend/app.py:26` set `WORKSPACE_ROOT = E:\gameforge_step1`. `toolchain.py:116`,
`live_editor.py:84`, `game_tools.py:97` and `unreal_tools.py:18` default to `E:\UE\UE_5.7`. The host profile JSON
(`configs/host_profiles/dev-rx7700xt.json`) already holds these values but no code reads it. The product cannot run on
another machine.

### F-06 (S2) Wrong default model — resolved by P0
`desktop/main_window.py:346,566`, `desktop/panels/chat_panel.py:501,557`, `backend/session_manager.py:54,72` and
`backend/app.py:45` default to `gameforge-27b-sft` (5.4 tok/s, 4K context). The Blueprint's own routing table names
`gameforge-qwen3.5-9b` as the planner and author (63.9 tok/s, 64K tested). The screenshot `reports/ide_ui_20261031.png`
shows the 27B selected.

### F-07 (S2) Provenance residue in the character pipeline — resolved by P0
`pipeline/character_pipeline.py:145-153` still resolves Epic's `FbxEditorAutomation/AnimatedCharacter.fbx` and writes
it into `diagnostics["import_source_fbx"]`. The same file labels a project-owned procedural asset with
`license_name="CC-BY-4.0"` (line 161). Neither is used for an import any more, but both are misleading provenance. This
is the defect class the 2026-10-30 audit was about.

### F-08 (S2) Port collision with UE 5.8 Unreal MCP — resolved by P0
The GameForge bridge defaults to `127.0.0.1:8000` (`launcher.py:53,88`; `GameForgeBridgeClient.cpp:24-25`). UE 5.8's
experimental Unreal MCP plugin also defaults to `http://127.0.0.1:8000/mcp` (Epic docs). On a 5.8 engine with MCP
enabled the two would collide.

### F-09 (S2) Verification depends on the foreground window and on a pawn that may teleport — resolved by P3
- `unreal/real_input.py` needs the game window in the foreground (`NotForegroundError`). The 2026-10-30 notes say Windows
  refuses foreground focus while the user works in another app. Unattended verification is therefore flaky by design.
- The PIE demos move a `DefaultPawn` with `pie_move_player_to` (`SimpleMoveToLocation`), which **snapped** in the
  packaged kit check (11–17 m legs completed in ≤ 0.01 s; `context.md`, packaged kit run 2). Their traversal claims are
  `[UNVERIFIED]` until they are re-run with leg-speed checks.
- Acceptance comes from per-demo hand-written checks. Nothing generic is derived from the game's own win and lose
  conditions.

### F-10 (S2) The op API has no argument schemas — resolved by P0 (scaffold) and P2 (enforcement)
The agent sees `unreal_editor(op=<enum of ~120>, args=<free object>)`. Arguments are validated only inside the editor,
and inconsistently. A wrong argument name costs an editor round trip and often fails silently with defaults
(`d.get("x", default)` in `_vec`).

### F-11 (S3) A 173 KB monolithic editor-op file — resolved by P0
`gameforge_ops.py` mixes 15 domains in one file. That has already caused one decorator re-binding bug (fixed
2026-10-31 with a unit test). Splitting it into a package is mechanical and low risk if the `dispatch` entry point
and `@op` names stay the same.

### F-12 (S3) Recipes duplicate gameplay code — resolved by P5/P6
Five `templates.py` files (5,808 lines) each emit their own Character, GameMode, HUD and self-test C++. The kit
(`GameForgeRuntime`) already has reusable actors, but no recipe uses them. AD-3 ("gameplay kit over templates") was
adopted on 2026-10-30 and never applied.

### F-13 (S3) Packaged games use the Development configuration and are ~860 MB — resolved by P10
`toolchain.py:307` defaults `package(configuration="Development")`. A blank UE5 Shipping build is about 321 MB
uncompressed (third-party measurement, UE 5.3). Shipping, plugin trimming and compressed paks should bring a generated
game well under 400 MB. **Pitfall:** Shipping compiles out `UE_LOG`, so the current `GF_SELFTEST PASS` log check fails
on Shipping builds. P3 replaces log scraping with a scenario result file.

### F-14 (S3) The IDE is a code IDE with game features bolted on — resolved by P4
From `reports/ide_ui_20261031.png`:
- The activity rail and the dock tab bar both switch the same four views (duplicate navigation).
- The start-screen actions ("New Prompt", "Open Folder…", "Mission Control") render as plain text, not buttons.
- A permanent terminal takes a fifth of the chat column.
- The right column spends its space on a static engine-install table.
- There is no Design view (spec), no build timeline as a primary surface, no evidence gallery and no "change this game"
  flow.
- "Check Ollama" is a developer action on the main toolbar.

### F-15 (S3) Dependency and package hygiene — resolved by P0
- `numpy` and `Pillow` are imported by product code (`pbr_texture_generator.py`, `sfx_synth.py`,
  `game_pipeline.py:_image_content`) but are missing from `requirements.txt` and `pyproject.toml`.
- `pyproject.toml` names the project `gameforge_bench` and exposes the entry point `src.gameforge_ide.launcher:main`
  (a `src.` import).

### F-16 (S3) Plugin descriptor claims — resolved by P0
`GameForge.uplugin` says it connects "to the IDE and local GameForge 27B model". It also lists `CreatedByURL`,
`DocsURL` and `SupportURL` on `gameforge.ai`, a domain the project has not shown it owns. Replace these with neutral
text and empty URLs.

### F-17 (S3) Documentation sprawl and a 150 KB append-only context file — resolved in this session (§5)
- There were 13 root narrative documents, 4 obsolete docs, 6 archived plans, and three overlapping "active plans"
  (Master Blueprint v2, Master Roadmap, Antigravity handoff).
- `context.md` was a 648-line log with several contradictory "current state" sections. Its section C described only
  the benchmark era, and section G was frozen at 2026-10-27.
- `README.md` described the 2026-10-19 benchmark starter pack.

### F-18 (S3) Hosted tier never exercised — resolved by P9
`backend/providers/hosted.py` has been tested only against a local HTTP/SSE mock (9 tests). The product's stated
target tier (Blueprint v2 §3) has never produced a game.

### F-19 (S3) Local models are weakly specialised — resolved by P9
The LoRA runs (loss 9.0 → 4.4 over 478 samples) are small. The models scored 73.8 % (4B) and 71.2 % (9B) on the
in-house 16-task code benchmark, which measures code Q&A, not agentic game construction. No evaluation measures what
GameForge actually asks a model to do: write a spec, patch a spec, write a custom rule, repair a compile error.

### F-20 (S3) Content quality ceiling — resolved by P7
Vegetation in the village is placeholder cones and spheres. The humanoid is a 754-vertex procedural prototype, and the
motion clips are kinematic. Better sources are already licensed for use in Unreal projects and present on this machine
or one Fab click away: engine Manny/Quinn, the Game Animation Sample (400+ animations added in 5.7, motion matching),
Megascans via the installed Fab/Quixel plugins, and the 5.7 MetaHuman Character scripting API. They are unused.

### F-21 (S3) Neural "BLOCKED" verdict is out of date — re-evaluated in P9
Current AMD documentation lists the RX 7700 XT (gfx1101) as supported by the HIP SDK on Windows. Community projects
report Hunyuan3D-2.1 shape generation working natively on Windows ROCm 7.2, and TRELLIS.2 on RDNA3 under Linux. The
correct status is "**BLOCKED (needs install approval + a measured 12 GB spike)**", not "impossible on AMD".
